# 標籤規則

> **版次**：`labels-v1.1`。這個版次只屬於本檔，與 plugin 的版本號分開。
>
> **改本檔的固定步驟（同版次）**：
> 1. 改本檔的同一個 PR 裡，升檔頭版次（`labels-v1.1`、`labels-v1.2`…；整套重訂才升 `labels-v2.0`），並在檔尾「版次紀錄」加一行。
> 2. 合併進 fork `main` 之後，在 fork 建 GitHub Release，tag `labels-v<版次>`，說明寫版次紀錄那一行：`gh release create labels-v<版次> --target <40 碼 SHA>`。`--target` 一律給完整 40 碼 SHA（`git rev-parse` 取），短碼會被當成分支名而失敗。
> 3. 若私有擴充設定了本檔的副本（例如 Heptabase 副本卡），照私有擴充 `setup.md` 寫的位置與做法同步。
>
> 本檔是「有哪些標籤、怎麼掛」的唯一權威；各 skill 的步驟引用本檔，不重抄表格。建標籤照第八節：`setup` 拿本檔的表格比對 repo 現有的標籤，用 `gh label create` 建缺的，名稱與顏色照本檔表格。

標籤是票清單上的看板：擁有者不必點進票就看得懂每張票是什麼、多急、要怎麼驗、做到哪、在哪台機器上。每一次改標籤都綁在流程本來就有的動作上（開票、領票、回報、關票），由使用端的每日稽核抓狀態與機器標籤的不一致；開票自檢只查格 1、2、6、9。

## 一、標籤清單

### ① 類型：開票時必掛，一張票一個

| 標籤 | 意思 | 顏色 |
|---|---|---|
| `錯誤` | 結果不對、壞掉 | `#5319E7` |
| `新功能` | 新的功能或模組 | `#7057FF` |
| `改善` | 改進既有功能、重構，不加新功能 | `#9A8CFF` |
| `文件` | 文件、註解、文案 | `#C5BEF7` |
| `維護` | CI、套件升級、設定雜項 | `#D4C5F9` |
| `資安` | 權限、secret、個資外洩 | `#3B0A9E` |

### ② 優先度與嚴重性：開票時必掛，一張票一個，擁有者隨時可以改

| 標籤 | 意思 | 顏色 |
|---|---|---|
| `P0-阻斷` | 生產壞了或有資安事故，其他工作先停 | `#B60205` |
| `P1-高` | 這批一定要完成 | `#FB8C00` |
| `P2-一般` | 照排程處理 | `#FBCA04` |
| `P3-低` | 有空再做 | `#CCCCCC` |

判斷依據：

- **P0**：生產壞了、或正在發生的資安事故。
- **P1**：有外部期限（例：活動日前一定要上線的那一批）、現在就有曝露的資安洞（例：端點沒有守門）、或擁有者當天拍板要做的。
- **P3**：內文寫明擱置或「現在不要做」的，以及不影響結果的小項。
- 其餘 **P2**。

### ③ 驗證分級：開票時必掛，一張票一個

驗證分類以本段為唯一權威；拆票、審查都引用這裡，不另寫一份。

| 標籤 | 判準 | 驗收 | 誰驗（一律不是施工的 session，見下） | 顏色 |
|---|---|---|---|---|
| `輕驗證` | 不改行為：文件、註解、標籤、改完看得到的小設定 | CI 綠 | 驗證者（另一個 session） | `#C2E0C6` |
| `中驗證` | 改到行為，不屬於下面五類 | CI＋突變（只突變這次新增或改動的斷言）＋真環境讀回一次＋對照組 | 驗證者（另一個 session） | `#0E8A16` |
| `重驗證-自檢` | ②密鑰與共用設定（secret、雲端權限綁定、DNS）④不可逆的正式環境操作（刪除資源、改寫 git 歷史或 force-push、正式資料庫 migration 或資料搬移、對外送出）⑤寫入或傳出個人資料 | 中級全部＋該類專屬證據（見下） | 驗證者（另一個 session） | `#F9A825` |
| `重驗證-外審` | ①部署管線本身（`.github/workflows/`、部署流程與部署目標；只開關日誌或追蹤這類可逆、改完看得到的設定不算）③存取控制、權限、身分判斷 | 中級全部＋換廠牌的對抗式外審 | 驗證者（另一個 session）送外審（只送改動處）並判讀結果 | `#D93F0B` |

- **誰驗**：施工的 session（含它派出的子代理）不能驗自己的成品，驗收由另一個 session 做。施工者自己跑的 CI、測試與證據照樣貼在票上，那是交件的內容，不算驗收。
- **除了 SPEC 與協調類票（第七節），每張票都要掛**，含不寫程式的決定票、擁有者操作票、查證票。只有討論、規劃、文件 → `輕驗證`。
- **同時碰到多類取最重的**；⑤同時碰到存取控制 ⇒ 算③。判斷不出來 → 指揮台裁定。
- **重驗證-自檢的專屬證據**：
  - ②從真實環境讀回（例如查 DNS 紀錄、列出 secret 名稱）＋對照組，並查 log 沒有印出密鑰原文。
  - ④執行前貼 dry-run 輸出，擁有者核准才執行。
  - ⑤列出這次寫入與傳出的每個欄位，逐欄寫理由。
- **重驗證-外審**：提示詞寫成對抗式（任務是「試著弄壞它」）；①要求逐行讀部署計畫的輸出（例如 Terraform plan）。送審一律走同一支送審腳本；腳本的位置由私有擴充指定。換廠牌做不到時（例如額度用完）的替代做法只有一種，寫在 `review` 第 4 節。外審的結論由總驗收通過的那個 session 留在每張外審票上（格式見第三節），開整合 PR 的人照它判斷能不能開（`pr` 第 3 節）。
- **驗收結果怎麼處理**：
  - 真缺陷一律擋合併，不准記成「不擋」再事後開修正票。**⑤類的發現一律算真缺陷。**
  - 只缺測試（程式本身是對的）不擋合併：一次列完，施工者在整合分支裡補一次，不回頭複驗。
  - 合併後由閘門票從真實環境讀回。
- **閘門票**：只讀、不改正式環境 → `輕驗證`；閘門裡含上面五類的動作 → 照該類掛。

### ④ 狀態：隨流程更換

每個 repo 只用一種記法，寫在 repo 設定的「施工狀態記法」：

- **狀態標籤**（`labels`）：用下表三個標籤。
- **Project Status**（`project`）：狀態記在 GitHub Project 的 Status 欄位，**不掛**`施工中`、`待驗證`。Project 與選項的 ID 寫在該 repo 的 repo 設定，不寫在這裡。Status 的選項名用 `In Progress`（或 `施工中`）與 `待驗證`：使用端的每日稽核只認這三個值當「有人在做」。

兩種記法同時用會不一致（Status 沒有自動規則跟著標籤改），所以一個 repo 只留一處。

| 標籤 | 狀態 | 誰在什麼時候改 | 記法 | 顏色 |
|---|---|---|---|---|
| `施工中` | 有人正在做 | 施工者領票時 | 只在 `labels` 記法建 | `#1D76DB` |
| `待驗證` | 做完了，等驗證 | 施工者回報時 | 只在 `labels` 記法建 | `#5DADE2` |
| `<等待擁有者>` | 等擁有者合併、部署或拍板 | 開 PR 的人，或需要擁有者決定時 | 兩種都建 | `#D6007A` |

- 還沒開工不掛；完成就關票。
- **`待驗證` 誰拿掉**：驗收是整批一次（`review` 改動模式，沒有逐票驗收）。總驗收通過、這批的 `重驗證-外審` 票都留了結論之後，**由指揮台拿掉這批票的 `待驗證`**；驗證的 session 不改標籤。`project` 記法沒有這個標籤：Status 在這時候要改成哪個選項，repo 設定沒寫就問擁有者，不自己挑。
- **等待擁有者的標籤名由 repo 設定「等待擁有者的標籤名」給**（建標籤時照這個名字建）。它是常設標籤：兩種記法都建，**永遠不刪**，沒有票在用也要在。
- 被前置票擋住：不另記，由原生 `blocked-by` 記錄。
- **等待擁有者的標籤掛兩種票**：① 有 PR 開著等擁有者合併；② 內文寫明要擁有者決定或操作，**而且**沒有開著的前置票、內文沒寫「可以繼續擱置」。被擋住的等前置票關了再掛。擁有者每天看的「在等他的事」＝這個標籤（用 Project 記法的 repo 再加 Status 的等待值）。
- 換狀態標籤用一條指令同時加新的、拿掉舊的：`gh issue edit <N> --add-label <新> --remove-label <舊>`（只改標籤、不動內文）。
- 一個 repo 從標籤記法改成 Project 記法：先把開著的票的狀態搬進 Status，再刪 `施工中`、`待驗證`——沒有開著的票使用時才刪，還有票在用的保留並列給擁有者（數票的指令見第八節）。

### ⑤ 現在在哪一台機器做：只在票開著、而且有人正在處理時掛

| 標籤 | 意思 | 顏色 |
|---|---|---|
| `<機器 A>` | 現在處理這張票的人在機器 A 上 | `#006B75` |
| `<機器 B>` | 現在處理這張票的人在機器 B 上 | `#1B9AAA` |

- **標籤名由 repo 設定「機器標籤名」給**；不給就不建。機器名與主機名的對應放私有擴充。
- 是誰在做不用標籤，看留言署名的「執行者」欄（第三節）。
- 換手時，機器標籤跟著狀態一起換，永遠指向現在處理這張票的那一台。
- 票關閉時，機器標籤拿掉。

票清單上看起來像（名稱是虛構的）：

```
app-12  錯誤    P1-高    重驗證-外審  施工中  機器A
        → 去機器 A；誰在做看票上最後一則施工署名
web-209 新功能  P2-一般  重驗證-外審  機器B     （Status：In Progress）
```

## 二、衍生票：掛 `衍生` 標籤，標題不加編號

| 標籤 | 意思 | 顏色 |
|---|---|---|
| `衍生` | 施工、驗證、外審中**意外冒出**、超出原票完成定義的工作 | `#FEF2C0` |

- **怎麼開**：施工者、驗證者不自己開衍生票，先記在 SPEC（留言），由指揮台開。先記成 SPEC「延後」、之後才開的票，仍算衍生。
- **什麼不算衍生**：照設計票或 SPEC **拆出來的施工票是計畫內的工作，不掛 `衍生`**，掛 SPEC、內文第一行寫「依 #N 設計」。統計衍生張數要回答的是「做的過程中冒出多少計畫外的事」，混進計畫內的票，數字就沒有意義。
- **衍生票直接掛 SPEC**：開票時掛到原票所屬的 SPEC 底下成為直接子票（衍生票再衍生也一樣掛 SPEC），同時掛 `衍生`，再加必掛三組。SPEC 的進度條、閘門與「查可開工」只看 SPEC 的直接子票，掛在原票底下會被靜默漏看。
- **和原票的關係用三樣東西表達**，不用上層票：①內文第一行寫「從 #N 衍生」②原票留言連結這張衍生票 ③`blocked-by` 依真正受影響的那一步設（方向不一定是原票擋衍生票，可能是衍生票擋原票）。
- **標題不加 `[#N-01]` 這類前綴**，照一般票命名。GitHub 搜尋會忽略 `[`、`#` 等符號，用標題前綴統計數不準。
- **「從哪張衍生」不做成標籤**：一張原票一個標籤會讓標籤數無限膨脹；內文第一行與原票留言已經記著。
- 開票自檢腳本查「掛了 `衍生` 的開著的票，上層必須是 SPEC」。
- 退場：GitHub 哪天原生支援「依上層票的類型篩選」，就撤掉這個標籤，改用原生篩選。

## 三、留言署名：記錄誰做過

施工回報與驗證回報的最後一行一律附署名，格式是「角色｜機器｜執行者｜分支」：

```
— 🔨 施工｜機器A｜session <session 前 8 碼>｜分支 fix/12-null-check
— 🔍 驗證｜機器B｜session <session 前 8 碼>｜分支 fix/12-null-check｜結果：通過
— 🔍 驗證｜機器A｜驗證子代理 agent-<agent 前 8 碼>@<session 前 8 碼>｜分支 fix/12-null-check｜結果：通過
```

- **執行者**：對話本身寫 `session <session id 前 8 碼>`；子代理寫 `施工子代理／驗證子代理 agent-<自己的 agent id 前 8 碼>@<派它的對話 session id 前 8 碼>`。子代理與派它的對話共用 session id，寫上 agent id 才分得出是同一個 session 裡的哪一個在做。
- 驗證回報在分支之後加「結果」欄。
- **總驗收的結論留言**（`review` 第 3.6 節）：「分支」寫受審的整合分支，執行者寫做出通過判定的那個 session，例：`— 🔍 驗證｜機器B｜session <session 前 8 碼>｜分支 <整合分支>｜結果：通過`。這一行必須是留言的最後一個非空行，開 PR 的人只認這個形狀；「結果」後面恰好是「通過」才算通過。
- **不驗自己的票**：施工的 session（含它派出的子代理）不能驗自己的成品，驗收由另一個 session 做。比對執行者欄、兩邊都取出 session（`session <id>` 取 id；`agent-<id>@<session>` 取 `@` 後面）：驗證者與施工者的 session 相同 ⇒ 違規。所以同一個對話派出的兩個子代理，一個施工、一個驗證，也違規。
- 標籤（和 Project 記法的 Status）負責「現在在哪一台、做到哪」，署名負責「誰做的」。要找現在是誰在做，看最後一則施工署名的執行者欄。

## 四、關票原因：不用標籤

| 情況 | 做法 |
|---|---|
| 做完 | PR 合併時自動關票；合併後還有擁有者的步驟 → PR 寫 `Refs`，不寫 `Closes`；`Refs` 的票步驟做完後由指揮台關 |
| 重複 | `gh issue close <N> --duplicate-of <原票>` |
| 不處理、不成立 | `gh issue close <N> --reason "not planned"` |
| 資訊不足 | 在票上留言 @對方，不關票 |

## 五、GitHub 預設的 9 個英文標籤

| 預設標籤 | 處理 |
|---|---|
| `bug`、`documentation`、`enhancement` | 改名成 `錯誤`、`文件`、`改善`（已掛的票自動跟著改）。新名已經存在時不改名，列出來手動合併 |
| `duplicate`、`wontfix`、`invalid`、`question`、`good first issue`、`help wanted` | 刪除。刪前先查有沒有票在用，有的話保留並列給擁有者決定 |

## 六、套用範圍

- **套用**：擁有者自己開票的 repo。
- **不動**：別人主導的 repo。別人的票只留言，不改標籤。

## 七、票種決定要掛哪些組（從標題前綴判斷）

| 票種 | 標題前綴 | 類型 | 優先 | 驗證 |
|---|---|---|---|---|
| 一般票 | 其他所有前綴（`[施工]`、`[實作]`、`[修正]`、`[決定]`、`[查證]`、`[外審]`…）與沒有前綴 | ✅ | ✅ | ✅ |
| SPEC | `[SPEC]` | ✅ | ✅ | — |
| 協調類 | 標題以「協作指揮台」開頭 | — | — | — |

- 只認兩個例外（`[SPEC]`、協作指揮台），其他一律當一般票——**不維護前綴清單**，新前綴出現也不必改表或改腳本。
- 開票自檢腳本用同一張表判斷。
- 補掛既有的票時：只加標籤，不改標題與內文；衍生票照第二節補掛 `衍生`；等待擁有者照第一節④；不補機器；已關的票不動。

## 八、建標籤：照本檔表格用 `gh label create` 建缺的

由 `setup` 做，不跑腳本；做完一次把結果告知擁有者（第 6 步的讀回）：

1. **讀 repo 現有的標籤**：`gh api --paginate "repos/<owner>/<repo>/labels?per_page=100" --jq '.[]|[.name,.color]|@tsv'`。
2. **對本檔的表格**：要有的標籤＝第一節①②③、第一節④（`labels` 記法才建 `施工中`、`待驗證`；等待擁有者的標籤兩種記法都建）、第一節⑤（repo 設定有機器標籤名才建）、第二節的 `衍生`。名字取自 repo 設定（施工狀態記法、機器標籤名、等待擁有者的標籤名）。
3. **已有相近名稱的先問擁有者**（例如 `bug` 之於 `錯誤`、`類型:維護` 之於 `維護`、大小寫不同的同名）：沿用（改名成本檔的名字）還是另建。第五節的預設英文標籤照第五節處理，改名用 `gh label edit <舊名> --name <新名>`。
4. **只建缺的**：`gh label create <名> --color <本檔的顏色，不含 #> --description "<本檔的意思>"`。同名已存在的不重建；顏色不同的列給擁有者看，要改才 `gh label edit <名> --color <色>`。
5. **刪標籤前先數票**：刪標籤會把它從所有票上拿掉。數票走 API（`gh api "repos/<o>/<r>/issues?state=all&labels=<urlencode 後的標籤>" --paginate`），有票在用的保留並列給擁有者決定。
6. **讀回**：再跑一次第 1 步，逐個對到本檔表格才算建好。

- **不用 `gh label clone`**：它把來源 repo 的現況當成第二份清單，本檔才是唯一權威。
- **不設組織的預設標籤**：組織預設會套到同仁新開的 repo（第六節：別人主導的 repo 不動）。
