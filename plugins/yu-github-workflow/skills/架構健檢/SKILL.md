# 架構健檢

找出值得重構成「深模組」的地方：讓小的介面後面藏住大量行為，改起來集中在一處、測起來走同一個介面。**這支只產出報告，不改任何原始碼、不開票、不進質問。**

## 1. 先讀私有擴充

照 [私有擴充](${CLAUDE_PLUGIN_ROOT}/references/private-extension.md) 的三步讀這支 skill 的補充（skill 名 `架構健檢`）：

1. 用 Bash 跑這一條，整條逐字照抄，不加引號、不接 `||`／`&&`、不改寫成 `echo`、`test` 或其他寫法：`printenv GITHUB_WORKFLOW_PRIVATE_DIR`
   - `printenv` 退出碼 1 且沒有輸出＝未設定；其他情況（被權限擋、工具錯誤、沒跑成）→ 停下告訴擁有者，不當成未設定。
2. 未設定 → 回報「私有擴充：未設定」，照本體做。**不讀任何私有檔。**
3. **有值才讀私有檔**：用 Read 讀 `<值>/架構健檢.md`。
   - 讀到 → 回報「私有擴充：已讀 架構健檢.md」，內容當補充規則，與本體一起遵守。
   - 讀不到 → 停下，告訴擁有者讀不到哪個路徑，不要照本體繼續。

私有擴充通常會指定三件事：**專案脈絡與規格／遷移計畫在哪**（第 3 節）、**報告寫到哪**（第 6 節）、**否決理由寫到哪**（第 8 節）。補充只能加、不能推翻本體；兩者衝突時把兩句並列給擁有者決定。

## 2. 用語

整份報告照這組詞寫，不換成「元件」「服務」「API」「邊界」這類鬆散的詞——用語一致就是重點。

| 詞 | 意思 |
|---|---|
| **模組** | 任何有介面、有實作的東西，不分大小：一個函式、一個類別、一個套件、一條跨層的切片都算 |
| **介面** | 呼叫者要正確使用它必須知道的一切：型別簽章之外，還有**不變量、順序限制、錯誤模式、必要設定、效能特性** |
| **深度** | 呼叫者（或測試）每學一單位介面，能用到多少行為。介面小、後面行為多＝深；介面幾乎跟實作一樣複雜＝淺 |
| **接縫** | 不改那個位置就能換掉行為的地方，也就是模組的介面所在的位置。接縫放哪是獨立的設計決定 |
| **轉接器** | 在接縫上滿足介面的那個具體東西。講的是它的角色（填哪個位置），不是它裡面有什麼 |
| **槓桿** | 呼叫者從深度得到的好處：一份實作在 N 個呼叫點、M 個測試上回本 |
| **局部性** | 維護者從深度得到的好處：改動、bug、知識、驗證集中在一處，修一次全部修好 |

### 三條判準（每個候選都要過）

1. **刪除測試**：想像把這個模組刪掉。複雜度跟著消失 → 它只是轉手，淺；複雜度散回 N 個呼叫端 → 它在幹活。要找的是「刪掉後複雜度會散開」的反面——**現在散在呼叫端、收進一個模組後會集中**的地方。
2. **一個轉接器＝假想的接縫，兩個才是真的**：只有一個轉接器的接縫不算數，不要為了「以後可能換」而建議加接縫；接縫兩邊真的有東西在變，才值得放。
3. **介面包含錯誤模式與順序限制**：判斷介面大小時，把「呼叫前要先做什麼」「失敗時會怎樣、呼叫端要怎麼接」一起算進去。型別簽章很小、但呼叫端得記住三條順序規則的模組，介面其實很大。

**不做平行設計多版介面**（派多個子代理各設計一版再比較）：那會大量消耗 token、重掃已經掃過的程式。這支只找候選，介面怎麼設計留給之後的質問。

## 3. 先定範圍，再讀脈絡

**範圍**：

- 擁有者有指方向（一個模組、一個子系統、一個痛點）→ 照方向，不另推。
- 沒有 → 用 `git log --oneline`（必要時加 `--name-only`）往回看一段，找最常改的檔與目錄，**只掃那裡**。不常改的地方重構了也回不了本。改動很分散、看不出熱點 → 再把範圍放寬，並在報告寫明放寬了。
- 範圍定好先講一句「這次掃：<路徑>，理由：<擁有者指定／log 熱點>」。

**脈絡**（掃之前讀）：

- 讀該 repo 的**專案脈絡**與**規格／遷移計畫**，位置照私有擴充；沒有私有擴充、或擁有者說沒有這類檔 → 在報告開頭寫明「未讀專案脈絡」，強度一律假設程式會長期存在。
- 讀**已拍板的決定**（位置照私有擴充）：被否決過的候選，除非否決理由已經不成立，否則不再提；要重提時在候選裡寫明「曾被否決，理由是…，現在不成立因為…」。
- **強度要考慮「這段程式還活多久」**：已排定要退場、要搬走、要整段改寫的程式，做深回不了本，最多列 `Speculative` 或放進「不值得動」。

## 4. 派子代理掃描

派一個子代理（範圍大、明顯分成兩塊時最多兩個，各掃一塊、不重疊）掃第 3 節定好的範圍。交代它：

- 照第 2 節的用語與三條判準找，**不要套固定的檢查清單**，記下讀起來卡住的地方：
  - 要懂一個概念，得在很多小模組之間跳來跳去；
  - 淺模組：介面幾乎跟實作一樣複雜；
  - 為了好測而抽出來的純函式，真正的 bug 卻藏在怎麼呼叫它（沒有局部性）；
  - 緊耦合的模組越過接縫互相洩漏；
  - 沒有測試、或從現在的介面很難測的地方。
- 每條發現都附**檔案路徑與行號**，以及它做刪除測試的結果。
- **只讀不改**：不改任何檔、不 commit、不呼叫遠端服務。

## 5. 一手查核

子代理的每一條結論，**寫進報告前由自己回原始碼查核**：打開它指的檔與行號，確認那段程式真的長那樣、刪除測試的結果真的成立。

- 查核成立 → 可以寫進「候選」。
- 查核不成立（行號對不上、行為跟描述不同、其實已經有測試或已經集中）→ 不進候選；寫進「不值得動」並註明「子代理提出，查核不成立：<一句理由>」。
- 沒查核的結論不寫進報告。

## 6. 寫報告

**格式**：一份 **Markdown** 檔。不做 HTML、不引用 CDN、不畫需要瀏覽器才看得到的圖。

**寫到哪**：擁有者這次有指定 → 照指定；私有擴充有指定 → 照擴充；都沒有 → 寫到系統暫存目錄（`$TMPDIR`，沒有就 `/tmp`）下的 `architecture-check-<時間>.md`，讓 repo 裡不多出檔。寫完告訴擁有者絕對路徑。

**這支只寫報告那一個檔**；原始碼、設定、文件一個都不改。

報告的段落，依序：

1. **範圍與依據**：掃了哪裡、為什麼是這裡、讀了哪些脈絡檔（或「未讀專案脈絡」）。
2. **候選**：每個候選一小節，含
   - **檔案**：牽涉哪些檔與模組（附行號）；
   - **問題**：現在的結構造成什麼摩擦；
   - **做法**：白話描述要改成什麼樣子（只講方向，**不設計介面**）；
   - **好處**：用槓桿與局部性講，以及測試會怎麼變好；
   - **刪除測試**：刪掉它（或把散開的部分收起來）時複雜度會怎樣；
   - **還活多久**：依脈絡判斷這段程式的壽命，沒有脈絡就寫「未知，假設長期存在」；
   - **強度**：`Strong`／`Worth exploring`／`Speculative` 三選一。
3. **不值得動**：看過但不建議動的地方，每項一句理由（刪除測試不過、只有一個轉接器、程式快退場、查核不成立、曾被否決）。這段跟候選一樣重要：它讓下次不用重看。
4. **開票草稿**：每個 `Strong` 與 `Worth exploring` 候選一份，含標題、要解決的問題、完成時能看到什麼、建議的驗證方式。**只寫草稿，不開票**——交給開票的角色（指揮台）決定要不要開。
5. **最推薦先做哪個**：一個候選、一句理由。全部都是 `Speculative`、或什麼都沒找到 → 直接寫「這次沒有找到值得動的地方」，不要硬湊候選。

## 7. 報告出來就停

寫完報告、告訴擁有者路徑之後，問一句「要深入哪一個？」就停。

- **不自動進質問**：擁有者挑中哪個，由擁有者自己叫質問那類 skill。那類 skill 若是手動限定，只印出它的名稱請擁有者自己打，不要代叫、也不要自己照它的流程做。
- 不開票、不開分支、不改程式。

## 8. 否決理由留檔

擁有者否決某個候選、且理由**下次掃描還用得到**（不是「現在沒空」這種一時的理由）→ 把「候選＋否決理由＋日期」寫進專案的**已拍板的決定**，位置照私有擴充；擴充有指定由哪個角色寫，就交給那個角色。沒有私有擴充 → 把這段文字交給擁有者，請他決定放哪裡；不要自己在 repo 裡另建記錄檔。
