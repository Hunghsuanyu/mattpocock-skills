# 施工票寫法與踩坑

`to-tickets` 第 5、6 節的細節。每一條都是踩過的：失敗的長相幾乎都是「零錯誤訊息、讀起來像成功」。

## 一、檢核表：K 與 H

### K 要三件事都有

1. **一條可貼上就跑的指令**，不是描述。測試還沒寫的票，開票時就把測試檔名與函式名訂死——指令第一天就跑得動，只是會紅。
2. **通過條件不用判斷**：退出碼、行數、次數、SHA。「正常」「正確」「沒問題」不算。
3. **⬛ 對照組也是一條指令，而且會回不同的答案**。「把鎖拿掉 → 必須紅」不算；要寫成「`git stash`；同一條測試 → 退出碼非 0；`git stash pop`」。受測與對照回一樣的結果＝什麼都沒測到。

三件有任何一件做不到，就標 `H`，寫清楚由誰看、看什麼。不是每一列都該機械化：硬湊出來的假機械條件比誠實標 `H` 更糟。

- `K` 由施工者貼輸出；`H` 由擁有者或驗證者留言確認。
- **完成定義只引用 `K`**，`H` 另列。
- **開工前先確認是紅的**：K 指令在還沒施工時跑一次，應該失敗。開工前就綠＝這條 K 沒測到要改的東西。

### K 的指令放程式碼區塊，不放表格格子

表格裡的 `|` 要寫成 `\|` 才不會切欄，而施工者用 `gh issue view` 讀到的是原文 `\|`：貼進 `grep -E` 就不再是「或」（恆 0 命中、「不得出現」型斷言恆綠），貼進 `jq` 就是語法錯。表格只放代號、通過條件、指到程式碼區塊的一句話。

### 開工前置不是檢核項

檢核表回答「**做完了沒、做對了沒**」。「這張表現在是不是壞的」「某個鍵拍板了沒」「排程建立了沒」回答的是「**現在該不該動手**」——那是前置，寫在票首或獨立的開工前置段，不進檢核表。

判準一句話：**沒過就不該開始做的，是前置；做完才驗得了的，是檢核。**

把前置寫成 `H` 檢核項，再照「完成定義只引用 K」排除掉，結果就是可以在前提不成立時開工、關票。這條不是放寬「完成定義只引用 K」，是補上它沒說的那一半。

## 二、數字、行號、SHA

- **票上每個數字標「量於哪顆 SHA、用哪條指令」**。沒有當場重量的不要寫，改寫成「去量，指令是 X」。憑對話脈絡寫的數字，施工者得先推翻你才能開始做事。
- **不寫行號，寫可重跑的定位指令**。錨點連結綁 SHA 不會漂；散文裡的行號沒有任何東西綁住它，一天之後就可能對不上。
- **40 碼 SHA 一律 `git rev-parse <ref>` 取，不准從短碼往後補**。補出來的 40 碼形狀完美、前幾碼也對，連結卻是 404；只看形狀的檢查會判綠。

### 改名、搬家類的清查：跑兩個 pattern

只搜「帶 owner」的引用會漏掉只寫裸名的地方。兩類都要跑，並附對照組：

```bash
# 類別一：帶 owner —— 必須改
git grep -nIE "<舊owner>/(<前綴>)?(<repo1>|<repo2>)"
# 類別二：裸名 —— 名字沒變，但周邊敘述可能過期
git grep -nIE "(<前綴>)?(<repo1>|<repo2>)"
# ⬛ 對照組：換成不存在的名字，應回 0 檔
git grep -nIlE "(<前綴>)?(<不存在的名字>)" | wc -l
```

把這幾條直接放進票，施工者重跑就得到當下的清單。

## 三、並行判準：兩張票之間要不要設 blocked-by

| 兩張票之間 | 設定 |
|---|---|
| 改同一個檔、同一份共用設定（密鑰、雲端綁定、DNS），或有語意上的先後（A 的結果會改變 B 的做法） | 設 `blocked-by` |
| 只共用同一條部署線 | **不設**。分支可以並行；合併與部署由擁有者一次一張 |
| 都不碰 | 可以並行，各用獨立工作樹 |
| 判斷不出來 | 設 `blocked-by` |

- 判斷依據是票上寫的施工範圍（錨點與待辦列出的檔）。**開票時就逐對檢查**，不要只設邏輯先後。
- 同一個檔的那一列由 `anchor-overlap.sh` 機械檢查；共用設定與語意先後要自己逐對想。
- 施工中發現要改到票上沒列的檔：施工者在票上留言，由指揮台補 `blocked-by`。

`blocked-by` 決定順序；「要不要合成一張」是另一個問題（SKILL 第 4 節第 1 條）。

## 四、外審

外審是唯一在票被執行**之前**質疑票的關卡：施工與驗證讀的是同一張票，票上的檢核指令錯了，兩邊會一起錯、而且全綠。所以每開一張施工票就補設被 `[外審]` 擋，外審沒關，沒有人開得了工。

## 五、雙方要互相配合的票

一方先做、另一方配合時：

- 每張票加一段 `## 與對方的配合`：列出對方相關的票、誰先做、誰配合。
- 完成定義加一條 `K`：在每張配合票上留言，寫明做了什麼、對方要怎麼配合、PR 或 SHA。

  ```bash
  gh api repos/<o>/<r>/issues/<對方票號>/comments --jq '[.[]|select(.body|contains("<本票完整網址>"))]|length'
  # 通過：≥ 1
  # ⬛ 對照組：換一張沒留過言的票號 → 回 0
  ```

- 對方的票不論誰開的，都只留言、不改內文。

## 六、統計衍生票

用指令算，不手記：

```bash
# 某張 SPEC 底下的衍生票
gh api -X GET search/issues -f q='repo:<owner>/<repo> label:衍生 parent-issue:<owner>/<repo>#<SPEC 號>' --jq '[.total_count,[.items[].number]]'
# 某個 owner 底下全部
gh search issues --label 衍生 --owner <owner> --limit 1000 --json repository,number --jq length
```

某張票衍生了哪幾張：看原票留言（開衍生票時留的連結）。
