# 平行實作：一個對話當總指揮

目標：整份 SPEC 的票都做完、收在同一條**整合分支**上，最後只開一個 PR（整合分支 → main），由擁有者合併。

這個對話是**總指揮**：讀圖、派工、收件、派合併，自己不施工；驗收交給另一個 session。擁有者要插手某一張時，另開一個對話處理那一張。

## 1. 先讀私有擴充

照 [私有擴充](${CLAUDE_PLUGIN_ROOT}/references/private-extension.md) 的三步讀這支 skill 的補充（skill 名 `implement-spec`）：

1. 用 Bash 跑這一條，整條逐字照抄：`printenv GITHUB_WORKFLOW_PRIVATE_DIR`
   - `printenv` 退出碼 1 且沒有輸出＝未設定；其他情況（被權限擋、工具錯誤、沒跑成）→ 停下告訴擁有者，不當成未設定。
2. 未設定 → 回報「私有擴充：未設定」，照本體做。
3. 有值才讀私有檔：用 Read 讀 `<值>/implement-spec.md`；讀到就與本體一起遵守，讀不到就停下告訴擁有者讀不到哪個路徑。

沒有給 SPEC 的票號或網址 → 問「要做哪一份 SPEC？」，不要猜。

## 2. 讀圖

1. 讀 SPEC 與它的子票。子票不是步驟清單，是用原生 `blocked-by` 排好的**擋關係圖**；任何時刻都有一批「可開工」的票（前置票都關了、自己還開著）。
2. 用「查可開工」列出這一批：SPEC 的子票裡，`blocked-by` 全部已關閉、本身還開著、還沒有人領的**施工票**。`[外審]`、`[開票] 下一階段`、決策票（`[決定]`／`[查證]`／`[操作]`）這類不會合進整合分支的子票不派給施工子代理：它們由指揮台、擁有者或另一個 session 處理，這個對話只把它們列出來。
3. 整合分支：**名字只從 SPEC 第 2 段「範圍」讀**（名字的唯一來源，規則見 [SPEC 範本](${CLAUDE_PLUGIN_ROOT}/skills/to-spec/references/spec-template.md) 第 2 段）。SPEC 沒寫 → 停下請指揮台寫進 SPEC 內文，不自己取名、不另記在留言。遠端還沒有這條分支就從 main 開。整合分支不是部署線，合併子代理可以合進去；**main 只有擁有者按**。

## 3. 先派探路子代理

開工前派一個**探路子代理**：讀票的錨點與相關程式、必要的外部文件，把筆記存在 **repo 外**一個所有子代理都讀得到的目錄。之後的施工子代理只讀筆記＋自己票上的錨點，不重讀同一批程式。

## 4. 派施工子代理

- **派工只傳連結**：SPEC、票、探路筆記、相關 commit 的網址或路徑；不轉貼票的內容。共同紀律只寫一行：「有私有擴充就照它指的檔」——不手抄紀律內容。
- 每個施工子代理：
  - 叫 `implement` 那支 skill 做一張票（Skill 工具，或照它的步驟）；
  - 自己的工作樹，**從整合分支開**；開工前確認工作樹的基底是整合分支，不是就重設到整合分支上；
  - 做完回報前，先把整合分支最新的 tip 合進自己的分支；
  - 合進整合分支之前，在本機跑該 repo CI 同一套指令並把輸出貼在票上。
- **碰同一批檔的票合成一個子代理**依序做完，不要各派一個：兩張票要讀懂的是同一份 context（同一個模組、同一支腳本、同一條機制）時，第二個子代理會從零重讀一遍。跨 repo、中間要等擁有者合併的兩步合不了。
- 施工子代理盡量在背景跑。**並行上限：本機測試同時最多 2 個**，其他子代理照常讀碼、改碼，輪到了再跑測試；其餘盡量多開。
- 施工中冒出的新工作：施工子代理只在 SPEC **留言**，不改 SPEC 內文；由指揮台寫進「尚未定義」段，在做決定時統一處理（要做的開票、不做的寫進「刻意不做」）。

## 5. 合併另派，驗收交給另一個 session

- **合進整合分支由另派的合併子代理做**，不是施工的那一個。合完之後，可開工的票變多了就再派施工子代理。
- **merge commit 訊息不帶分支名**：合併一律 `git merge --no-ff -m "<不含分支名、票號的英文訊息>" <分支>`；不用 git 預設的訊息（預設會寫進兩邊的分支名，分支名常含票號）。理由見 [維護規則](${CLAUDE_PLUGIN_ROOT}/references/maintenance.md)「外洩檢查」。
- **驗收由另一個 session 做，整批一次，不逐張**：這個對話與它派出的每一個子代理都算施工方，**不派驗證子代理驗自己這批的成品**。`review` 沒有逐票模式，流程固定是：
  1. 施工子代理回報後，票換成待驗證（照 `implement` 第 6 節），合進整合分支；
  2. 整批施工票都收齊之後，交另一個 session 跑 `review` 改動模式（總驗收），對整條整合分支審一次（第 6 節）；
  3. 總驗收通過後，做出通過判定的那個 session 在這批每張 `重驗證-外審` 票各留一則結論（`review` 第 3.6 節）；
  4. 之後由指揮台拿掉這批票的 `待驗證`。
- 交給總驗收 session 的三條，缺一不可：
  1. 驗證的 session 不是這一個，也不是它派出的子代理；
  2. 用全新的工作樹，從受驗的 SHA 開，不進施工者的工作目錄；
  3. 交接只給票、受驗 SHA 與整合分支，**不轉述施工子代理的回報或推理**——驗證方只讀票與程式碼。
- 交接的方法：印出這批票（名稱做成連結）、整合分支與受驗 SHA，請擁有者另開一個對話跑 `/yu-github-workflow:review`；這個對話不代叫、不代驗。
- 施工子代理的署名執行者欄寫 `施工子代理 agent-<自己的 agent id 前 8 碼>@<這個 session id 前 8 碼>`；「不驗自己的票」就比對這一欄。格式以 [labels.md](${CLAUDE_PLUGIN_ROOT}/references/labels.md) 第三節為準。

## 6. 收齊之後

1. 全部的**施工票**都合進整合分支後（`[外審]`、`[開票] 下一階段`、決策票不合進整合分支，不算在這個條件裡），交給 `review` 改動模式對**整條整合分支**的改動審一次（總驗收，交接照第 5 節）。`review` 設了 `disable-model-invocation`，而且驗收要由另一個 session 做：印出 `/yu-github-workflow:review` 與要審的整合分支，請擁有者在另一個對話打。
2. 審查發現的問題**交一個子代理一次修完**，不拆票。
3. 複驗一樣交給另一個 session，**只複驗修過的地方**，不整套重跑。
4. **PR 收齊後才開一個**：整合分支 → main，交給 `pr` 那支開；不提早開草稿 PR（每次 push 都會跑 CI；同 repo 的 PR 會跑分支裡的 workflow、拿得到 secret）。驗證等級要求外審的，外審與各外審票上的通過結論在開 PR **之前**做完（沒有結論 `pr-risk.sh` 回 3，開不了）。
5. 進度看 SPEC 的子票清單與「已經做的決定」段，不另做進度表；收尾條件只看施工票。
6. 收尾：清掉所有施工、合併子代理的工作樹（`git worktree remove --force <路徑>`），拆完看 `git worktree list`。

多子代理並行時的暫存檔、量測污染與工具用法見 [parallel-agents.md](${CLAUDE_PLUGIN_ROOT}/skills/implement-spec/references/parallel-agents.md)。
