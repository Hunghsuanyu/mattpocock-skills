# 寫規格：把談完的決定寫成一張 SPEC 票

這支只寫、不訪談。決定已經在對話裡談完了，這支把它們整理成一張 SPEC 票，同時開出外審票與「[開票] 下一階段」票。**規格直接寫在 SPEC 票裡**，不另寫規格檔，也不寫計畫檔——計畫就是之後拆出來的施工票。

## 1. 先讀私有擴充

照 [私有擴充](${CLAUDE_PLUGIN_ROOT}/references/private-extension.md) 的三步讀這支 skill 的補充（skill 名 `to-spec`）：

1. 用 Bash 跑這一條，整條逐字照抄，不加引號、不接 `||`／`&&`、不改寫成 `echo`、`test` 或其他寫法：`printenv GITHUB_WORKFLOW_PRIVATE_DIR`
   - `printenv` 退出碼 1 且沒有輸出＝未設定；其他情況（被權限擋、工具錯誤、沒跑成）→ 停下告訴擁有者，不當成未設定。
2. 未設定 → 回報「私有擴充：未設定」，照本體做。**不讀任何私有檔。**
3. **有值才讀私有檔**：用 Read 讀 `<值>/to-spec.md`。
   - 讀到 → 回報「私有擴充：已讀 to-spec.md」，內容當補充規則，與本體一起遵守。
   - 讀不到 → 停下，告訴擁有者讀不到哪個路徑，不要照本體繼續。

## 2. 不訪談，只寫

- **不開一輪提問**。決定還沒談完（範圍、做法、取捨講不清楚）→ 停下，建議擁有者先用質問類或 brainstorming 類 skill 把決定談完，再回來叫這支。不要在這支裡自己問一輪。
- 只有兩件事要在動筆前問擁有者，其他都不問：
  1. **驗在哪一層**（範本第 5 段）：擁有者在對話裡已經講明 → 照寫，不再問。沒講 → 提一個建議（用既有的接縫、用最高的那一層、層數越少越好），問擁有者同不同意，得到答案才寫。
  2. **這張是下一階段的 SPEC**（由某張「[開票] 下一階段」票要開出來的）→ 動筆前先問一句：「先跑一次架構健檢？」擁有者說要 → `arch-check` 設了 `disable-model-invocation`（只能手動叫）：只印出 `/yu-github-workflow:arch-check`，請擁有者自己打，跑完再回來寫；不代叫，也不用其他方式照它的流程做。說不要 → 照寫。架構健檢不自動跑。

## 3. 讀現況

- 讀 repo 的 `docs/agents/github.md`（repo 設定），確認票開在哪個 repo、施工狀態記法。沒有這個檔＝還沒導入，先走 `setup`。
- 只讀這批改動會碰到的檔，取得第 4 段「影響盤點」要的數字。**每個數字附 SHA 或可重跑的指令**（`git rev-parse` 取完整 SHA，不從短碼補），寫明量於哪一天。
- 讀不到、量不到的，寫「沒量到」，不換成推測。

## 4. 照範本寫內文

範本在 [spec-template.md](${CLAUDE_PLUGIN_ROOT}/skills/to-spec/references/spec-template.md)，寫之前先 Read 它。

- **12 段全部保留、順序不動**；用不到的段寫「無」，不刪。
- 內文只用範本的 12 個二級標題（`## `）；段內分小節用三級以下標題。範本裡的 `> 寫法：…` 說明行換成實際內容。
- **第 8 段「退場」必填**，不能寫「無」：什麼情況撤掉、誰在什麼時候判斷、判斷要讀的資料現在有沒有在寫。
- **第 9 段「開工前置」與第 7 段「完成定義」分開**：沒過就不該開始做的是前置；做完才驗得了的是完成定義。
- **第 10 段「已經做的決定」**：開 SPEC 時已經談定的決定，每條一行 `[名稱](連到談定那則留言)：一句結論`。
- **第 11 段「尚未定義」**：看得到但還說不清楚的事寫這裡，不硬切成票。SPEC 開出來之後，施工者看到的新事在 SPEC 留言，由指揮台寫進這段；施工者不改 SPEC 內文。
- 給擁有者看的地方講票用名稱、號碼做成連結；給機器的（`blocked-by`、指令參數）照舊用號碼。
- 指程式碼的連結一律用 SHA 固定連結，不用分支名。

## 5. 寫完自我檢查

逐段對照對話與量測結果：

- **出現擁有者沒講過的東西＝錯**。改掉，或把它拿出來問擁有者，不留在內文裡。量到的事實（附 SHA 或指令）不算「沒講過」。
- 12 個段名與順序和範本相同；沒有被刪的段；第 8 段不是「無」。
- **長度**：內文上限約 6.5 萬字元（GitHub 的上限）。超過時，主內文只放摘要與決定，細節拆成留言，每則留言第一行寫它屬於哪一段（例：「第 4 段 影響盤點（細節）」），主內文在該段放連結。

## 6. 開票

擁有者只要求寫檔、不開票 → 把內文寫到指定的檔就停，不呼叫 `gh`。其餘情況照下面開：

1. **SPEC 票**：標題 `[SPEC] <名稱>`；內文走 `--body-file`。標籤掛**類型＋優先**各一個，**不掛驗證**（SPEC 的票種規則以 [labels.md](${CLAUDE_PLUGIN_ROOT}/references/labels.md) 第七節為準）。
2. **同時開 `[外審]` 票**：`[外審] <SPEC 名>：規格對抗驗證`，用 `--parent <SPEC 號>` 掛成 SPEC 的子票，標籤照 labels.md 掛三組。開 SPEC 時施工票還沒開，所以**擋施工票這一步在拆票（`to-tickets`）做**：每開一張施工票就用 `--add-blocked-by <外審票號>` 補設。外審票沒關，沒有人開得了工。
3. **同時開「[開票] 下一階段」票**：用 `--parent <SPEC 號>` 掛成子票，標籤照 labels.md 掛三組。
   - **開票時機只看一件事：下一階段的票能不能定案**（內容不會再因為前面還沒做完的票而改變）。能定案 → 現在就可以開下一階段、送外審，不必等這一階段收尾；還不能定案 → 用 `blocked-by` 只擋在「會決定它內容的那一張票」後面，不擋在整個階段的最後面。
   - **開票和施工是兩件事**：施工的先後由各施工票自己的 `blocked-by` 表達，這張票不替施工排隊。
   - 下一階段的 SPEC 開出來時，裡面再排一張「[開票] 下一階段」票，規則自己延續。
   - 已經確定沒有下一階段 → 不開這張，在第 6 段「刻意不做的事」寫一句理由。
4. 開完讀回：`gh issue view <SPEC 號> --json title,labels,body` 確認標題、標籤、12 個段名；兩張子票確認掛在 SPEC 底下。

## 7. 交回

回報 SPEC 與兩張子票的名稱（號碼做成連結），以及下一步：

- 路線已經清楚、可以切成施工票 → `to-tickets`。
- 還有一串決定要一題一題做 → `wayfinder`（決策子票掛在這張 SPEC 底下）。

## 8. 界線

- 只寫 SPEC 與它的兩張子票；不開施工票（那是 `to-tickets`）、不施工。
- 不改別人的票；不對外送出任何訊息。
- SPEC 開出來之後，內文只有指揮台改；其他人在 SPEC 留言。
