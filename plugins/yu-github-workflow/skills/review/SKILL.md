# 審查：兩軸審一段改動，疊上驗證分級

這支**只能由擁有者自己打 `/yu-github-workflow:review` 叫用**。其他 skill 或總指揮走到要審查的時候，只印出這個指令請擁有者打，不代叫，也不照本檔的流程自己做。

審查只報告、只送審；修交給另派的子代理（第 5 節）。不合併、不部署、不開 PR（開 PR 是 `pr` 那支）。

## 1. 先讀私有擴充

照 [私有擴充](${CLAUDE_PLUGIN_ROOT}/references/private-extension.md) 的三步讀這支 skill 的補充（skill 名 `review`）：

1. 用 Bash 跑這一條，逐字照抄：`printenv GITHUB_WORKFLOW_PRIVATE_DIR`
   - `printenv` 退出碼 1 且沒有輸出＝未設定；其他情況（被權限擋、工具錯誤、沒跑成）→ 停下告訴擁有者，不當成未設定。
2. 輸出是空的（變數沒設）→ 回報「私有擴充：未設定」，照本體做。
3. 有值 → 用 Read 讀 `<值>/review.md`。
   - 讀到 → 回報「私有擴充：已讀 review.md」，內容當成補充規則，與本體一起遵守。
   - 讀不到 → 停下告訴擁有者讀不到哪個路徑，**不要照本體繼續**。

補充只能加、不能推翻本體；兩者衝突時把兩句並列給擁有者決定。

## 2. 選模式

| 模式 | 審什麼 | 什麼時候 |
|---|---|---|
| **改動模式**（總驗收） | 整合分支對預設分支的整段改動 | 一次上線的範圍全部合進整合分支之後、開整合 PR 之前，審一次。沒有逐票驗收：施工票換成待驗證後等整批收齊，在這裡一起驗 |
| **規格模式** | SPEC＋這批全部的施工票（還沒有程式） | 施工票全開完之後、任何人開工之前 |

擁有者沒講是哪一種、或給的東西對不上任何一種 → 問，不要猜。

**誰審**：驗證方，不是施工者，也不是開票的人；施工的 session 與它派出的子代理都不能審自己的成品。**不驗自己的票**：比對留言署名的執行者欄，判準見 [labels.md](${CLAUDE_PLUGIN_ROOT}/references/labels.md) 第三節；驗證回報照同一節的署名格式，在分支之後加「結果」欄；改動模式的「分支」寫受審的整合分支。

## 3. 改動模式

### 3.1 釘住基準點

1. 基準點＝預設分支（通常是 `origin/main`），審的是整合分支。先 `git fetch origin`。
2. 先確認兩端都存在、改動不是空的，**不對就在這裡停**，不要帶著壞的基準點派兩個子代理：
   ```bash
   git rev-parse --verify origin/main origin/<整合分支>
   git diff --stat origin/main...origin/<整合分支>   # 空的＝沒有東西可審
   ```
3. 記下兩條指令交給子代理：改動 `git diff origin/main...origin/<整合分支>`（三點，對 merge-base 比）、commit 清單 `git log origin/main..origin/<整合分支> --oneline`。

### 3.2 找規格

規格＝這條整合分支所屬的 SPEC 票＋它底下的全部施工票（整合分支的名字寫在 SPEC 第 2 段「範圍」）。用 `gh issue view` 讀 SPEC 與每一張子票的內文。找不到 SPEC → 問擁有者；擁有者說沒有 → Spec 軸跳過，最後報告寫「沒有規格可對照」。

### 3.3 找寫法文件

找出 repo 裡所有講「程式該怎麼寫」的文件（例：專案的指令檔、`CONTRIBUTING.md`、`CODING_STANDARDS.md`）。有 `CONTRIBUTING.md` 或 `CODING_STANDARDS.md` 就一定要列進去。repo 設定 `docs/agents/github.md` 的「特殊禁忌」不是 `無` → 它底下的「特殊禁忌」段也列進去，改動違反任何一條就報。

Standards 軸另外一律帶下面這份**壞味道基準**（Fowler《重構》第 3 章），repo 什麼都沒寫也照用。兩條規則：

- **repo 文件優先**：repo 文件明寫允許、而基準會標的，不標。
- **都是提醒**：每一條都標成「可能是 X」，不是硬違規；工具已經會擋的不報。

每條是「是什麼 → 怎麼改」，拿來對改動：

- **名字看不懂**：函式、變數、型別的名字說不出它做什麼、裝什麼。→ 改名；想不出老實的名字，代表設計還沒想清楚。
- **重複的程式**：同一個邏輯形狀出現在改動的多個段落或多個檔。→ 抽出共同的形狀，兩邊都叫它。
- **羨慕別人的資料**：一個函式碰別的物件的資料比碰自己的多。→ 把它搬到它羨慕的資料那邊。
- **資料總是成群出現**：同樣幾個欄位或參數總是一起傳（一個型別想被生出來）。→ 包成一個型別，傳那一個。
- **基本型別撐場**：用字串或數字代表一個值得有自己型別的概念。→ 給它一個小型別。
- **重複的分支判斷**：同一個 `switch`／`if` 串對同一種型別，在改動裡出現好幾次。→ 換成多型，或兩處共用一張對照表。
- **散彈式修改**：一個邏輯上的改動，逼得改動散落在很多檔。→ 把會一起改的東西收進同一個模組。
- **發散式修改**：同一個檔為了好幾個不相干的理由被改。→ 拆開，讓每個模組只為一個理由改。
- **預想的通用性**：為規格沒有的需求加的抽象、參數或掛鉤。→ 刪掉；等真的需要再加。
- **訊息鏈**：呼叫端得一路 `a.b().c().d()` 走下去。→ 在第一個物件上用一個方法把這段路藏起來。
- **中間人**：一個類別或函式幾乎只是轉手。→ 拿掉它，直接叫真正的對象。
- **拒絕繼承**：子類別或實作者忽略、覆寫了大部分繼承來的東西。→ 不用繼承，改用組合。

### 3.4 兩軸各派一個子代理，平行審

兩個子代理**同時派出**，各自獨立，讓兩軸不互相污染：

- **Spec 子代理**，交給它：改動指令與 commit 清單、SPEC 與全部子票的內文。任務：「列出 (a) 規格要求了、卻沒做或只做一半的；(b) 改動裡規格沒要求卻多做的；(c) 看起來做了、但做法看起來錯的。每一條都引用規格原句。400 字內。」
- **Standards 子代理**，交給它：改動指令與 commit 清單、3.3 找到的文件清單、**3.3 的壞味道基準全文**（它沒有別的地方讀得到）。任務：「逐檔或逐段列出 (a) 違反 repo 文件的地方，引用那份文件與那一條；(b) 看到的基準壞味道，寫出名稱並引用那一段。分清楚硬違規與提醒：違反 repo 文件可以是硬的，基準壞味道一律是提醒，repo 文件優先於基準。工具已經會擋的不報。400 字內。」

沒有規格（3.2）→ 只派 Standards，報告裡寫明 Spec 軸沒審。

### 3.5 彙報：分開報，不合併、不重排

用 `## Spec`、`## Standards` 兩段原樣（或稍微整理）列出兩個子代理的報告。**不合併、不重新排序**——一段改動可能完全照規格卻壞了 repo 的寫法，也可能寫法全對卻做錯了東西；混在一起排，一軸會把另一軸蓋掉。

最後一行：每軸各幾條、各軸最嚴重的一條。不跨軸挑「最嚴重的一條」。

### 3.6 通過之後：在每張外審票留結論，交回指揮台

**通過**＝兩軸沒有真缺陷（第 5 節），而且第 4 節要求的證據與外審都做完、外審結論是通過。

1. **在這批每張 `重驗證-外審` 票上各留一則結論**（內文走 `--body-file`）：審了什麼（整合分支與受審 SHA）、外審用了哪種做法（換廠牌，或第 4 節的替代做法）、結論、連到總驗收報告。最後一行署名，開 PR 的人照這個形狀認結論：
   ```
   — 🔍 驗證｜<機器>｜session <這個 session id 前 8 碼>｜分支 <整合分支>｜結果：通過
   ```
   留的是做出「通過」判定的那個 session：第一次就通過＝這一輪總驗收的 session；修完才通過＝做複驗的那個 session（第 5 節）。由對話本身留，不交給子代理。
2. **不通過不留**：不在任何票上留「結果：通過」；發現照第 5 節處理，修完複驗通過才留。開 PR 的人在外審票上找不到通過的結論，整合 PR 就不開（`pr` 第 3 節）——這是刻意的。
3. **交回指揮台**：印出這批票的名稱（號碼做成連結）與「總驗收通過，可以拿掉待驗證」。**拿掉 `待驗證` 由指揮台做**，這個 session 不改標籤（labels.md 第一節④）。

## 4. 疊上驗證分級：決定審多深

驗證分類只有一份：[labels.md](${CLAUDE_PLUGIN_ROOT}/references/labels.md) 第一節③。讀範圍內每張票的驗證標籤，照它做；同一批裡最重的那一級決定這次要不要外審。

- **只驗這次改動的地方**：改到的程式、對應的測試與突變、改動碰到的邊界。**不整套重跑**；全套交給 PR 上的 CI。
- **`中驗證` 以上**：
  - 突變只突變這次新增或改動的斷言，不跑全量。兩個方向都要：改回壞的樣子必須紅，還原必須綠。
  - 真環境讀回一次，配一個對照組。受測與對照回一樣的結果＝這一輪什麼都沒測到。
- **`重驗證-自檢`**：加上該類的專屬證據（labels.md 第一節③）。
- **`重驗證-外審`（①部署管線、③存取控制與身分判斷）**：換廠牌的對抗式外審，**一定在開整合 PR 之前做完**——同一個 repo 的 PR 會用分支裡的 workflow 跑、拿得到 secret。只送改動處；①要求逐行讀部署計畫的輸出。送審手法見 [external-review.md](${CLAUDE_PLUGIN_ROOT}/skills/review/references/external-review.md)；有私有擴充就照它的送審流程。
  - **換廠牌外審做不到時（例如額度用完）的替代做法**：改由另一個 session 派多條獨立子代理，從不同角度審查同一批改動處（規格模式是同一批票；例：失敗路徑、權限與身分判斷、部署目標、與規格的出入）；子代理彼此看不到對方的結果。「另一個 session」在改動模式指不是施工的 session，在規格模式指不是開票的 session（第 2 節「誰審」）。結論註明用了替代做法與換廠牌做不到的原因（3.6 的結論留言、規格模式的外審票留言都要寫）。替代做法的發現一樣照第 5 節先複核再改。這是唯一的例外，其他情況照樣換廠牌。
- **票上的檢核標了外審級的**，由驗證方對改動處重跑一次，不只看施工者貼的輸出。
- **不等、不請人測**：不寫「等幾小時再看」「請人實測」。我方觸發一次、讀回兩端的一手紀錄、配對照組，測過就算驗收。只有我方工具碰不到的地方才請擁有者做一個動作，請之前先想自己有沒有路。

## 5. 發現怎麼處理

- **真缺陷一律擋合併**，不記成「不擋」再事後開修正票。**⑤（寫入或傳出個人資料）的發現一律算真缺陷。**
- **只缺測試**（程式本身是對的）不擋：一次列完，在整合分支裡補一次，不回頭複驗。
- **外部模型提的每一條修正，先用自家模型複核**：對照這批工作的目標與程式邏輯，符合才改；不符合的不改，在外審票或驗證回報留言寫「不採納＋為什麼」。照單全收＝把外部模型的錯寫進施工者唯一會讀的那份文件。
- **修法交一個子代理一次修完**，不拆票。**只複驗修過的地方**；修的與驗的不是同一個 session（修的可以是原施工者；派修的 session 連同它派出的子代理都算修的一方，複驗交給另一個 session）。
- 複驗時問「這次的修法各自可能弄壞什麼」，不只問「舊問題消失了嗎」——修一輪本身會帶進新缺陷。

## 6. 規格模式：開工前審票

外審是唯一在票被執行**之前**質疑票的關卡：施工與驗證讀同一張票，票上的檢核寫錯了，兩邊會一起錯，而且全綠。

**前提**：這批已經有一張外審票，設成每一張施工票的前置（`blocked-by`），所以外審票沒關，沒有人開得了工。沒有這張票 → 停下告訴開票的人，不要直接開審。

**只派一軌**：指的是改票的權限只給一軌（見下面「改票的界線」）。這一軌照第 4 節的替代做法派多條子代理審查不衝突——那些子代理只回報發現，不改票。步驟：

1. **準備送審材料**：SPEC 與全部施工票的純文字副本。只送副本，見 [external-review.md](${CLAUDE_PLUGIN_ROOT}/skills/review/references/external-review.md)；導出的指令與要附哪些檔，有私有擴充就照它。
2. **換廠牌送審**，不要用開票的同一個模型——同一個模型只會補錯字、補遺漏，不會推翻自己的假設。提示詞寫成對抗式（任務是「試著弄壞它」）。換廠牌做不到時，照第 4 節的替代做法，並在外審票留言註明。
3. **每一條修正先用自家模型複核**（同第 5 節）。
4. **複核通過的才改票**。改完在外審票留言列出「動了哪幾張票的哪一段」，然後關外審票 ⇒ 前置自動解除，施工可以開工。

**改票的界線**：外審票**還開著**的期間，**只有這一軌**可以直接改施工票的內文（那批票全被外審票擋著，沒有施工者在動它們）。外審票一關，立刻回到常態：內文只有指揮台改，其他人只留言。內文是整份覆蓋、兩邊同時改會互蓋而不報錯，所以外審只派一軌，這條不因階段放寬。
