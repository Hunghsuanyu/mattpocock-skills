# GitHub 工作流入口

這支只做兩件事：**判斷這次該用哪一支 skill 並帶過去**，以及**讓每一支都共用的幾條原則在動手前就在眼前**。各步驟的細節在各支 skill 本體，這裡不重複。

## 0. 先讀私有擴充

照 [私有擴充](${CLAUDE_PLUGIN_ROOT}/references/private-extension.md) 的三步（skill 名 `github-workflow`）：

1. 用 Bash 跑這一條，逐字照抄：`printenv GITHUB_WORKFLOW_PRIVATE_DIR`
   - `printenv` 退出碼 1 且沒有輸出＝未設定；其他情況（被權限擋、工具錯誤、沒跑成）→ 停下告訴擁有者，不當成未設定。
2. 輸出是空的（變數沒設）→ 回報「私有擴充：未設定」，照本體做。
3. 有值 → 用 Read 讀 `<值>/github-workflow.md`。
   - 讀到 → 回報「私有擴充：已讀 github-workflow.md」，內容當成補充規則，與本體一起遵守。
   - 讀不到 → 停下告訴擁有者讀不到哪個路徑，**不要照本體繼續**。

補充只能加、不能推翻本體；兩者衝突時把兩句並列給擁有者決定。

## 1. 判斷該用哪一支

先弄清楚兩件事：**這是哪一個 repo 的工作**（讀該 repo 的 `docs/agents/github.md`；沒有這個檔＝還沒導入，先走「設定」），以及**現在是哪個角色在做**（見第 3 節）。然後對照下表：

| 情況 | 用哪一支 |
|---|---|
| 新 repo 要導入這套流程、建標籤、寫 repo 設定 | `setup` |
| 一批新工作要寫成 SPEC（範圍、決定、驗在哪一層、退場） | `to-spec` |
| SPEC 已經有了，要拆成施工票、設先後 | `to-tickets` |
| 工作大而模糊，路線還看不清，要先一題一題做決定 | `wayfinder` |
| 別人開的、外來的票要分流（不是我方自己規劃的票） | `triage` |
| 領一張票照票做完 | `implement` |
| 一次跑完整份 SPEC，派子代理平行施工、收進整合分支 | `implement-spec` |
| 審查一段改動（規格與標準兩軸，疊上驗證分級） | `review` |
| 開 PR、寫 PR 內文 | `pr` |
| 換對話、換機器、交給別人接手 | `handoff` |
| 開下一階段之前看整體架構 | `arch-check` |

「我想開一張票」不是一個動作：先問清楚是**一批新工作**（`to-spec`）、**從現有 SPEC 拆出來**（`to-tickets`），還是**施工中看到的新事**（不開票，見第 2 節原則二）。判斷不出來就問擁有者，不要自己挑。

**怎麼帶過去**：

1. 用 Skill 工具叫 `yu-github-workflow:<名稱>`。
2. 回錯誤說這支設了 `disable-model-invocation`（只能手動叫）→ 只印出 `/yu-github-workflow:<名稱>`，請擁有者自己打。**不要代叫，也不要用其他方式照它的流程做**。
3. 回「找不到這支 skill」→ 停下告訴擁有者缺哪一支，不要自己即興照做。

## 2. 兩條總原則

### 原則一：該講的話放在該張票上，其他地方用連結指過去

例外四條：

1. **要機器執行的不只放票上**：hook、檢查腳本、指令放進 repo 或 plugin 的腳本，票上放連結。文件裡的 shell 只能被審查、不能被測試。
2. **跨票的長期決定**：「票關了還要留下的決定」，在關 SPEC 時由指揮台謄進長期的家（位置由私有擴充指定）。新對話不會主動翻已關的票。
3. **連結一律用 SHA 固定連結**：指程式碼不用分支名，檔案搬移或刪除後舊連結仍讀得到原內容。
4. **票的內文只一人改，其他人留言**：`gh issue edit --body-file` 是整份覆蓋，兩邊同時改會互蓋而且不報錯。內文只有指揮台改；施工、驗證只留言。**唯一例外**：外審票開著的期間，只派一軌外審，那一軌可以直接改被這張外審票擋住的施工票內文（那批票全被擋著，沒有施工在動它們）；外審票一關，立刻回到常態。

### 原則二：新工作在「做決定」時處理，施工只照票做完；一次上線的範圍做完才審一次

- **施工不開票**：施工中看到新的事，在 SPEC **留言**，由指揮台寫進「尚未定義」段；施工者不改 SPEC 內文。指揮台在做決定時統一處理（要做的開票、不做的寫進「刻意不做」）。
- **不能等的立刻報**：資安、個資、正式環境壞掉 → 在 SPEC 留言標 🔴，指揮台當場開票。
- **票切得夠小**：一個對話做得完。施工中發現票太大 → 停下回報指揮台重切，不邊做邊開票。
- **審一次**：每張票做完合進整合分支；整合分支收齊後對整段改動審一次，發現的問題交一個子代理一次修完，只複驗修過的地方；審查與複驗都由施工以外的 session 做。整合分支 → `main` 只有擁有者按。

## 3. 角色

| 角色 | 做什麼 | 不做什麼 |
|---|---|---|
| **指揮台**（固定一軌） | 寫 SPEC、開票、做決定；改指揮台與票的內文；寫長期的家 | 不施工、不驗證 |
| **施工** | 一軌領一張票做到底：從整合分支開分支、讀窄搜寬、測試、push 自己的分支、在票上留言回報 | 不改票內文、不開票、不碰 `main`、不部署 |
| **驗證** | 驗別人施工的票，只驗這次改動的地方；外審票開著期間的那一軌，依原則一例外 4 可改施工票內文 | 不驗自己施工過的票：施工的 session（含它派出的子代理）不驗，驗收由另一個 session 做 |
| **總指揮** | 一次跑完整份 SPEC：派施工、合併的子代理，收齊後請擁有者在另一個 session 審一次、送外審，再開整合 PR | 不自己施工；不派子代理驗自己這批的成品 |
| **擁有者** | 決策、合併進 `main`、部署、對外動作、瀏覽器與帳號操作 | — |

各角色的細節在對應的 skill：施工見 `implement`、驗證見 `review`、總指揮見 `implement-spec`。

## 4. 每種狀態只放一處

| 狀態 | 放哪裡 | 不放哪裡 |
|---|---|---|
| 票的先後順序 | 原生相依 `blocked-by` | 手寫佇列表、內文散文 |
| 一批工作的總表、進度、已經做的決定 | SPEC 的子票清單＋「已經做的決定」段 | 快照留言、自做網頁 |
| 施工狀態（施工中／待驗證／等擁有者） | repo 設定「施工狀態記法」指定的那一處（狀態標籤或 Project 欄位，擇一） | 兩處同時記 |
| 施工進度、回報、發現 | 票的留言 | 票的內文、個人待辦 |
| 「有這件事、去哪看」 | 個人待辦，只放指標（位置由私有擴充指定） | — |

**「等擁有者」是擁有者每天看的佇列**：只掛兩種票——有 PR 開著等合併；內文寫明要擁有者決定或操作、而且沒有開著的前置票。被擋住的不掛，由 `blocked-by` 記錄。標籤名由 repo 設定給，判準以 [標籤規則](${CLAUDE_PLUGIN_ROOT}/references/labels.md) 為準。

## 5. 每種資訊的家

| 資訊 | 家 | 誰寫 |
|---|---|---|
| 長期行為規則 | 專案的指令檔 | 指揮台 |
| 怎麼用 GitHub 的流程 | 這個 plugin | 擁有者合併 |
| 各 repo 自己的設定 | 該 repo 的 `docs/agents/github.md` | `setup` |
| 一批工作的範圍、設計、決定、進度 | SPEC 票＋子票 | 指揮台開，其他人留言 |
| 單張工作的步驟、計畫、檢核、回報 | 施工票（內文）＋留言 | 指揮台寫內文，施工留言 |
| 跨票的長期決定 | 長期的家（位置由私有擴充指定） | 指揮台，關 SPEC 時謄入 |
| 要機器執行的檢查 | repo 或 plugin 的腳本，票上放連結 | 施工 |

**設計與計畫都寫在票上，不另寫設計檔或計畫檔。** 長期的家只記跨批次的脈絡、已拍板的決定、開著哪些 SPEC（連結），不記票的進度。

## 6. 講票與量測

- **講票用名稱、號碼做成連結**：給擁有者看的回覆、摘要、指揮台寫票名，號碼做成連結；給機器的（錨點、`blocked-by`、指令參數）照舊用號碼。
- **原生功能先用**：GitHub 已經做好的功能先用；會增加步驟或會靜默漏資料的才不用。
- **標「未實測」的先測再用、附對照組**；寫著「不能用」的限制也會變，要用之前重跑一次。
